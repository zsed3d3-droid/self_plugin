# 근거 회수와 개인 오답노트 계약

이는 구현할 데이터·동작 기준이다. 현재 판단 동기화 도구는 검토 DB→파일의 추출/최신성 검사를 제공하며, 전체 수집·의미검색·재시도 런타임은 별도 개발/검증 항목이다.

## 같은 주제의 이력을 한곳에

프로젝트·주제·목적·기능을 분류 키로 사용한다. 요청/회의/할 일별 세션은 그 키와 안정적으로 연결하고 resume한다. 원천 이벤트→사용자 지적→AI 해석→실행→산출물→사용자 평가를 이벤트 ID로 연결한다. 최소 보존 정보는 다음과 같다.

- `project_id`, `topic_id`, `purpose`, `feature_id`, `session_id`
- `event_id`, `parent_event_id`, 사건 종류와 발생 시각
- 원문 출처/버전/위치와 사용자가 직접 쓴 말
- 해석한 규칙, 적용 범위, 반례, 실행 내역, 산출물 위치
- 기능 검증 상태와 사용자 만족/추가 교정의 별도 상태

원문을 AI 요약으로 덮어쓰지 않는다. 동일 이벤트의 재수집·판단 수정 버전은 독립된 반복 교정으로 세지 않는다. 토큰·비밀번호를 정제하고, 수정/삭제/보존 범위는 자료별 정책을 따른다.

## 처음부터 검색 목적을 충족

“일단 FTS만 구현하고 나중에 검색 품질을 해결”을 기본 경로로 삼지 않는다. 요구되는 검색은 다음을 포함한다.

1. 원문과 정확한 식별자를 찾는 어휘 검색.
2. 표현이 달라도 같은 경험을 찾는 의미검색.
3. 프로젝트·주제·목적·채택/거절·최신성·권한 범위 필터.
4. 현재 맥락을 반영한 후보 재정렬과 근거의 위치/버전 반환.
5. 오회수·오해석 피드백, 반례·대체 규칙과 다음 검색의 제외/보강.

표현·필터·re-ranking의 구성은 요구를 온전히 충족하는 가장 단순한 구현을 고른다. 사용자 원칙은 검색 성능에 필요한 투자를 아끼지 않는 것이며, 모든 프로젝트에 동일한 거대 스택을 무조건 설치하라는 뜻은 아니다. 임베딩·재정렬도 AI 기능이면 승인된 Codex 경로나 명시적으로 허용한 로컬 도구를 사용하고 새 유료 제공자를 몰래 추가하지 않는다.

검색 검증은 실제 과업 질의→관련 근거 ID→반례를 고정해 회수율·상위 정확도·지연·잘못 섞인 주제/폐기 규칙을 확인한다. 결과를 전부 읽지 못했는데 검색 완료라고 쓰지 않는다. 현재의 `route-development.py`는 상황별 스킬 경로 계획이며 이 검색 기능을 대신하지 않는다.

## 잘못된 회수와 잘못된 해석을 따로 고치기

원문이 틀렸는지, 이 과업과 무관한지, AI가 잘못 해석했는지 구분한다. 잘못된 회수는 해당 맥락에서 제외/하향하고, 의미가 필요한 원문은 보존하며 정정·반례를 붙인다. 다른 과업에서도 유효한 근거를 전역 삭제하지 않는다. 정정은 해당 근거/규칙 버전에 연결해 다음 검색과 해석에 반영한다.

## 반복 교정 승격과 평가

확인된 반복 교정은 같은 범위의 운영 규칙으로 승격하고 원천 이벤트·수정 결과·사용자 이유를 남긴다. 이미 명확히 요청한 반복 규칙에 매번 새 승인을 요구하지 않는다. 적용 범위가 상충하거나 모호하면 그 부분만 확인한다. 한 화면의 밀도 선호를 모든 화면의 보편 규칙으로 만들지 않는다.

기능 검증과 기호도는 별도 축이다. 사용자가 원하지 않는 결과는 테스트가 녹색이어도 수용된 결과로 표시하지 않는다. 정확성·보안·접근성은 지킨다. 반례나 선호 변화가 나오면 기존 버전을 지우지 않고 범위를 좁히거나 대체·rollback 이력을 남긴다.

## 재시도 소진 이벤트

작업 시작 시 시도 예산과 동일 실패의 식별 범위를 기록한다. 실패의 원인과 변경 가설이 달라지는 유효한 시도만 예산 안에서 수행한다. 상한 소진 시 다음을 남긴다.

`retry_budget_exhausted`: 작업/주제, 시도 횟수와 상한, 각 시도의 가설·오류·산출물, 남은 선택지, 사용자에게 필요한 판단.

해당 작업의 실행은 사용자 판단을 받을 때까지 중지한다. 새 세션·새 요청 ID·재시작으로 카운트를 초기화하지 않는다. 결과 불명인 외부 작업은 예산이 남아 있어도 중복 실행하지 않고 먼저 결과를 확인한다. 이 문서만으로 실제 Broker의 재시도 예산 집행이 구현된 것은 아니다.

## 테스트도 근거 중심으로 정리

주기적 작업 점검이나 테스트가 눈에 띄게 중복될 때 같은 동작의 중복을 parameterized/table 기반 검사로 묶는다. 제거할 테스트는 더 이상 소비되는 기능/계약이 없다는 근거를 남긴다. 서로 다른 독립적인 실패 신호는 유지한다. 테스트 수를 줄이기 위해 동작 검증을 생략하거나 실제 오류를 숨기지 않는다.
