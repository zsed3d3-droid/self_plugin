# 문장 교정 예시

아래는 문체 판단을 위한 가상 예시다. 각 행에 주어진 사실을 유지하며 고친다. 실제 답변은 현재 질문과 확인한 근거로 작성한다.

| 상황과 원문 | 다듬은 표현 | 판단 |
| --- | --- | --- |
| 설정이 B를 제어함. “이 설정은 A가 아니라 B를 제어합니다.” | “이 설정은 B를 제어합니다.” | 질문에 필요 없는 A를 덜어낸다. |
| 설명 대상이 A임. “여기서 B를 말하는 것은 아닙니다.” | “이 설명은 A에 관한 내용입니다.” | 알고 있는 실제 대상을 직접 쓴다. 대상이 불명확하면 확인한다. |
| 문서만 확인함. “B가 검증된 건 아닙니다.” | “확인 범위는 문서 검토까지입니다. B의 실제 동작은 추가 확인이 필요합니다.” | 확인 범위를 명시하고 미확인 상태를 유지한다. |
| 로컬 테스트 통과, 운영 검증 미실시. “A는 완료했지만 B는 검증된 게 아닙니다.” | “로컬 테스트를 통과했습니다. 운영 환경 검증은 미실시 상태입니다.” | 수행한 검사와 남은 검증을 구체적으로 쓴다. |
| 사용자가 작동 방식을 질문함. “핵심은 단순한 조회를 넘어 혁신적인 가치를 제공하는 것입니다.” | 확인된 조회 대상과 결과를 바로 설명한다. | 실제 기능을 알 수 없으므로 교정 과정에서 새 기능을 만들지 않는다. |
| “문서에 한정하여 답변합니다. A의 기능은 B입니다.” | “A의 기능은 B입니다.” | 출처는 기존 계약대로 연결하고 불필요한 정책 서론을 덜어낸다. |
| “분석을 완료했습니다. 이제 결과를 설명하겠습니다. A는 B입니다.” | “A는 B입니다.” | 생성·검토 과정의 예고를 덜어낸다. |
| 본문 설명 뒤 같은 내용을 “결론적으로 A는 B입니다”로 반복함. | 본문에서 설명을 마친다. | 같은 결론을 다시 적을 필요가 있는지 판단한다. |
| 확인한 두 페이지에 답이 없음. “이 문서에는 해당 정보가 없습니다.” | “확인한 두 페이지에서 해당 근거를 찾지 못했습니다.” | 검색·검토한 범위를 보존한다. |
| 아이디어만 제안함. “이 조합은 효과가 검증됐습니다.” | “제안: 두 항목을 조합합니다. 효과는 추가 확인이 필요합니다.” | 근거 없는 효과 확언을 제안과 필요한 확인으로 바로잡는다. |

## 반드시 남길 내용

- 질문이 “운영 검증도 끝났나요?”이고 아직 실행하지 않았다면 “아직 운영 검증을 실행하지 않았습니다”라고 직접 답한다.
- 원문 인용 `“25°C에서는 반응하지 않았다.”`는 그대로 보존한다. 온도·부정·인용 경계를 유지한다.
- 사용자가 휴지통 복구를 예상하지만 실제 삭제가 영구 삭제라면 “삭제하면 서버에서 즉시 영구 삭제됩니다. 복구할 수 없습니다”라고 결과를 알린다.
- 문서가 사용자의 전제와 다르면 해당 원문·조건을 제시한다. 정정을 위해 설명하는 차이를 유지한다.
- `실패`, `미실행`, `결과 미확인`은 각각의 상태를 유지한다. 문장을 매끄럽게 만드는 과정에서 다른 상태로 바꾸지 않는다.

## 구조화 답변

기존 계약이 `answer`, `limitations`, `evidence_ids`를 요구한다고 가정한다. 아래 값은 가상 예시다.

```json
{
  "answer": "A는 B 조건에서 수행합니다.",
  "limitations": ["C 조건의 측정 결과는 추가 확인이 필요합니다."],
  "evidence_ids": ["provided-source-1"]
}
```

스킬은 실제 서비스의 키·타입·허용 필드·근거 ID를 그대로 사용한다. 설명을 위해 예시의 키나 ID로 바꾸지 않는다. 본문에서 다루지 않은 새로운 사실을 한계 설명에 보태지 않는다.
