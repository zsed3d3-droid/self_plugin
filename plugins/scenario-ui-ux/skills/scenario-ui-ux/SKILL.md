# Scenario UI/UX

요구한 기능이 쉽게 이해되고 끝까지 수행되는 화면을 만든다. gstack의 요구·설계·리뷰·QA 흐름 안에서 이 스킬을 UI 전문 경로로 사용한다. 유명 스킬을 동시에 모두 로드하거나 같은 검수를 여러 번 돌리지 않는다.

gstack의 스타일 detector/체크리스트는 [적용 경계](references/gstack-adapter.md)를 따른다. 저자의 글꼴·크기·테두리 취향을 사용자 승인이나 접근성 표준으로 승격하지 않는다.

## 원천 적용의 실행 상태

[reference-adoption.md](references/reference-adoption.md)를 읽고 원문 확인·스킬 연결·실행·제품 적용을 구분한다. 공동 공식 skill 이름이 불명확한 경우에도 확인한 개별 공식 문서의 지식을 조건에 맞게 적용한다. 비교 미완료를 검증 후 제외로 표현하지 않는다. Anti-slop·Unslop UI를 모션 라이브러리로 분류하지 않는다.

## 우선순위와 범위

사용자의 현재 요구와 판단 이유 → 범위가 맞는 채택된 개인 규칙 → 프로젝트 계약·DESIGN.md → 이번 과업에 선택한 외부 근거 순이다. 기능·보안·접근성의 문제는 해결하고, 유효한 대안에서는 사용자 기호를 따른다. 높은 star 수와 외부 저자의 취향은 품질 보증이나 사용자 승인이 아니다.

- 개인화·여백·밀도·색·컨트롤 변경은 [personal-ui.md](references/personal-ui.md)를 먼저 읽는다. 좋아한 영역을 보존한다. 특정 프로젝트의 색상 선호를 모든 브랜드의 색상 금지로 확대하지 않는다.
- 작은 명확한 수정은 기존 DESIGN.md와 해당 컴포넌트의 근거로 바로 진행한다. 인터뷰·3안·전체 재설계·추가 승인·큰 모델의 허가를 강제하지 않는다.
- 신규 서비스의 컨테이너·health·영속 볼륨은 개발 하네스가 검사한다. MLX Metal 호스트 엔진만 승인된 예외다. 이 스킬을 이유로 새 프레임워크나 서비스를 추가하지 않는다.

## 1. 기능에서 화면 흐름을 정한다

저장소와 실행 화면을 확인하고 사용자/과업·진입·주요 행동·성공 결과·취소/실패 복구·기기를 짧게 기록한다. 신규 흐름은 text-wireframe-planner로 진입→행동→결과를 정한다. 요구를 노출 위치와 검증 시나리오에 연결한다. 이미 주어진 요구를 다시 묻지 않는다.

한 요청의 모든 입력·중간 상태·결과·후속 기능을 동시에 보여줄 필요는 없다. 현재 판단에 필요한 정보부터 보여주고 상세와 보조 작업은 명시적으로 연다. 자주 비교하는 정보를 불필요한 여러 단계로 쪼개지도 않는다. 목록/표+상세, 문서, 검색+결과, 단계형 입력 중 실제 과업에 맞춰 선택한다.

## 2. 레퍼런스에서 적용할 결정을 고른다

[reference-workflow.md](references/reference-workflow.md)를 읽고 실제 제품/오픈소스의 구조·상호작용을 조사한다. 아래 도구는 후보를 찾는 오프라인 태그 검색이다. 의미검색·시각 평가·브라우저 관찰을 수행했다고 주장하지 않는다.

```sh
python3 scripts/reference-plan.py --task "할 일 목록, 추가 모달, 상태 드롭다운, 기한 달력" --stack vanilla --limit 5
python3 upstream/ui-ux-pro-max/scripts/search.py "task list dialog focus keyboard" --domain ux --max-results 3
```

기본 화면 문법과 필요한 상호작용 근거를 고른다. 후보는 넓게 찾고 이번 결정에 필요한 것만 읽는다. 구조 비교가 중요한 신규 제품은 대안도 검토해 한 방향을 추천한다. 사소한 화살표 수정에 여러 제품 전체 조사를 강제하지 않는다.

레퍼런스를 실제로 열고 가능한 경우 캡처를 확인한다. URL 나열은 시각 검토가 아니다. 가져올 구조·간격 관계·컨트롤 행동과 버릴 장식·부적합한 밀도를 구분한다. 여러 저자의 팔레트·폰트·카드·그림자를 혼합하지 않는다. 기능과 실제 한영 콘텐츠를 대입해 맞는지 판단한다.

## 3. 구조 문제의 원인을 진단하고 고친다

캡처 도구는 이미 live-browser-session이 담당한다. 핵심은 무엇을 관찰하고 어떤 수정을 선택하느냐다. [runtime-ux-method.md](references/runtime-ux-method.md)와 [designer-judgment.md](references/designer-judgment.md)에서 현재 증상에 맞는 진단·해결 패턴만 읽는다.

10명의 UX 디자이너 원문과 조건별 판단은 같은 플러그인의 [ux-judgment](../ux-judgment/SKILL.md)로 연결한다. 증상/과업으로 후보를 좁히고 원문 주장·수정 가설·반례·동일 사례 검증을 읽는다. 전 저자의 철학을 매 제품에 동시에 적용하지 않는다. MengTo의 구체적 설계 명세·작은 반복·레퍼런스 비교는 [mengto.md](references/mengto.md), ThreeUI는 공간/시각 설명이 유용한 제품에서만 적용한다.

- 증상 → 과업에서 관찰한 행동 → 원인 가설 → 수정 → 같은 과업 재검증으로 연결한다. "답답하다"를 고정 padding 값으로 번역하지 않는다.
- 주행동이 묻힘, 입력/결과/후속 작업 혼재, 과도한 카드 경계, 반복 작업의 모달 비용, 숨긴 정보의 재탐색, 실패 시 초안 유실 등 구조·흐름 문제를 먼저 본다. 색만 바꿔 동선 문제를 해결했다고 하지 않는다.
- 디자이너의 경험은 적용 조건과 역효과 조건을 함께 읽는다. 유명인의 원문 주장, 에이전트 해석, 실제 실행 결과, 사용자 평가를 구분한다.
- 실사용자 연구를 수행하지 않았다면 휴리스틱 검토/과업 재현이라고 기록한다. AI가 수행한 테스트를 사용자 행동 연구나 만족도 검증으로 부르지 않는다.

## 4. DESIGN.md에 결정을 고정한다

프로젝트 DESIGN.md에 과업/화면별 위계, 주요 행동, 기본/확장 노출, 색·간격·타입·radius 토큰, 포커스·선택·오류·로딩·빈 상태, 작은 화면/모션 감소, 채택/제외 레퍼런스를 간결하게 적는다. 검사 가능한 값은 [templates/DESIGN.md](templates/DESIGN.md)의 design-contract에 둔다. 기존 토큰을 보존하고 필요한 수정만 한다.

실제 첫 UI scaffold와 DESIGN 계약이 준비되면 첫 브라우저 캡처·관찰 파일을 만들기 전에 `scripts/install-design-hooks.py --project /path/to/project`를 실행한다. 설치를 통과시키려고 가짜 UI 파일을 만들지 않는다. 설치기는 새/빈 `.design-audit`의 소유 marker만 만들며 검사 통과·예산·신뢰를 부여하지 않는다. 기존 managed 근거는 유지하고 비어 있지 않은 미관리 폴더나 symlink는 자동 채택하지 않는다.

같은 역할의 입력/버튼/포커스는 공용 컴포넌트와 토큰으로 맞춘다. 다른 과업의 밀도까지 획일화하지 않는다. 카드 경계는 독립 선택·비교·소유권에 필요할 때 쓰고 반복된 묶음은 정렬·여백·제목·구분선을 먼저 검토한다. 여백을 없애서 카드 문제를 해결하지 않는다.

sources/*-research.json에서 commit/경로/라이선스를 추적한다. sources/selected는 읽기 전용 참고 자료이며 전부 자동 활성화되는 스킬이 아니다. 원문 반입 여부는 개별 기록을 따른다. 웹 소개와 실제 저장소가 다르면 실제 확인한 범위를 말한다.

plain-writing으로 버튼은 행동, 오류는 원인과 복구를 말한다. 구현 용어를 제품 메뉴로 옮기지 않는다. 유료 UI 키트·폰트·이미지 자산은 기본으로 쓰지 않는다. 실제 아이콘·허용된 자산의 출처/라이선스를 보존한다.

기존 CSS/WAAPI로 충분하면 모션 라이브러리를 추가하지 않는다. React 복합 전환은 Motion 등을 필요한 경우만 선택한다. Vaul은 사용 허용 후보이며 사용자 교체 요청 없이 유지보수 상태만으로 배제하지 않는다. 고정 duration·모든 키보드 모션 금지·상시 장식 효과를 강요하지 않는다.

## 6. Hook으로 검사하고 수정 루프를 닫는다

[design-hooks.md](references/design-hooks.md)로 프로젝트 Hooks를 연결한다. 기존 훅/설정은 보존하고 Claude Code/Codex 이벤트와 호스트 신뢰 절차를 구분한다. 설정 생성만으로 실행·신뢰·통과를 주장하지 않는다.

- 수정 직후: 변경 범위의 토큰·간격·타입·공용 컨트롤 계약을 검사하고 위반 위치와 수정 근거를 에이전트에 돌려준다.
- 작업 완료: 기능 시나리오와 Live Browser Session 또는 gstack QA 한 경로, 실제 화면/DevTools 근거, 독립 읽기 전용 검수를 묶는다. 정적 토큰 통과는 정보 위계/UX 통과가 아니다.
- 위반: 원인을 고치고 같은 시나리오를 재실행한다. 프로젝트/과업별 예산 소진을 이벤트로 남기고 새 세션/요청으로 우회하지 않는다. Hook은 임의로 코드를 덮어쓰지 않는다.
- 전달/CI: 현재 입력 hash에 맞는 결과만 인정하고 필요한 단계 누락을 통과시키지 않는다. PostToolUse는 이미 수행한 쓰기를 취소하지 않는다. 배포 차단은 CI에서 gate 종료 코드로 집행한다. 통과가 자동 배포 허가는 아니다.

실제 브라우저에서 핵심 과업·작은 화면·긴 한영 문구·키보드·로딩/빈 상태/실패·모션 감소와 관련 반복 입력을 확인한다. 캡처를 직접 열어 위계·여백·경계·잘림을 보고 기능은 assertion으로 판정한다. 모션은 시작/중간/끝을 관찰한다. 접근성 자동 검사만으로 키보드·실제 흐름을 대체하지 않는다. 앱이 실행되지 않으면 이유와 미검증 범위를 남긴다.

## 7. 기능과 선호를 나눠 축적한다

[acceptance.md](references/acceptance.md)와 프로젝트 검증 기록에 사용자 원문·화면/기기/과업·해석·전후 결과·재평가를 연결한다. 채택/거절 이유는 프로젝트에 별도로 연결한 비공개 원문이 있을 때만 적용한다. 이 배포에는 개인 판단 snapshot이 없다. 기능 통과·코드 감사·시각 검토·사용자 평가는 서로 다른 상태다. 미평가 화면을 만족/승인으로 기록하지 않는다.
