# 검증 기록

구조·흐름 결함은 [runtime-ux-method.md](runtime-ux-method.md)의 증상→과업 근거→원인→수정→동일 과업 재검증으로 기록한다. 판단에 쓴 디자이너 경험은 [designer-judgment.md](designer-judgment.md)의 출처와 적용 조건을 연결한다. 원문의 주장과 에이전트 추론, 실제로 재현한 문제를 분리한다.

DESIGN.md의 정적 토큰 검사와 Hook/CI 실행 결과를 시나리오 근거에 연결한다. 토큰 통과·브라우저 assertion·화면 검토·독립 critique·사용자 기호는 각각 상태를 남긴다. 필수 단계 미실행, 이전 소스 hash, 인증 실패를 pass로 요약하지 않는다.

작은 수정은 결과에 몇 줄로 남긴다. 신규 흐름은 서비스의 기존 문서 위치에 다음을 정리한다.

| 시나리오 | 시작/역할 | 행동 | 관찰 가능한 결과 | 검증 방법/근거 | 상태 |
| --- | --- | --- | --- | --- | --- |
| S1 | 실제 또는 합성 상태 | 사용자가 수행한 행동 | 화면과 데이터 결과 | assertion/캡처 경로 | pass/fail/blocked/not-run |

스크린샷은 시각적 근거다. 클릭 성공·저장·권한·데이터 보존은 해당 assertion/API 결과와 함께 기록한다. 차단된 POST를 기능 성공으로 세지 않는다. 디자인 리뷰는 중요도·실제 근거·사용자 영향·수정안을 연결한다.

기능 검증과 사용자 선호는 별도로 기록한다. 기능이 통과해도 “너무 답답하다”, “카드가 많다” 같은 사용자 지적은 해결할 피드백으로 남긴다. 유효한 UI 대안 중에서는 사용자의 선호를 우선하며 정확성·보안·접근성 요구를 보존한다. 사용자 평가를 받지 않은 화면은 선호 미평가로 둔다.

밀도나 시각적 취향을 바꿨다면 해당 영역의 전후 화면, 사용자의 표현, 바꾼 요소, 평가를 [개인 UI 판단](personal-ui.md)의 방식으로 연결한다. 다른 프로젝트나 화면에서도 같은 취향이라고 추정하지 않는다.

대표 폭(예: 1440, 390, 320px), 긴 한영 텍스트, 200% 확대, 키보드 진입/ESC/포커스 복귀, 모션 감소를 화면에 맞게 선택한다. 반복 행·컨트롤의 높이와 테이블 가독성도 본다. 의도한 테이블 내부 가로 스크롤과 페이지 전체 넘침을 구분한다.

모션을 수정했다면 전환의 시작·중간·끝에서 좌표·텍스트·겹침을 확인한다. 초기 좌표에 잘못 나타나는 정보, 늦게 측정돼 튀는 레이어, 빠르게 다시 닫을 때의 잔상을 같은 재현 경로에서 재검증한다. 검증 범위는 변경과 실제 실패에 맞추며 작은 수정에 전체 제품의 새 테스트를 추가하지 않는다.
