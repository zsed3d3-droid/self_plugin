# 디자이너의 공개 경험에서 가져올 판단

확인일: 2026-10-29. 여섯 저자/실무자의 공개 글을 직접 읽고 문제별 판단으로 정리했다. 최신 게시물만을 모은 목록은 아니다. 유료 책·강의·에셋은 반입하지 않았다. 아래 **원글**은 저자가 공개한 설명/사례이며 **적용**은 이 플러그인의 해석이다. 예제 작업 앱에서 효과를 측정한 연구 결과가 아니다.

사용자의 현재 요구와 연결된 비공개 프로젝트 규칙의 채택/거절 이유가 우선한다. 새 저자의 취향을 승인된 개인 규칙으로 등록하지 않는다. 필요한 레시피만 선택하고 수정 결과를 [runtime-ux-method.md](runtime-ux-method.md)로 검증한다.

## D1. 같은 무게의 정보 → 과업별 위계

**Adam Wathan · Steve Schoger / Refactoring UI.** [공개 미리보기: Labels are a last resort](https://refactoringui.com/previews/labels-are-a-last-resort), [저자와 협업 맥락](https://refactoringui.com/).

- **원글의 개입:** 데이터의 모든 항목을 같은 `라벨: 값`으로 나열하면 위계가 약해진다. 문맥으로 뜻을 아는 값은 자체로 보여주거나 짧은 설명과 합친다. 반대로 사양 비교처럼 라벨을 찾아 읽는 과업에서는 라벨을 강조할 수 있다고 설명한다. **입력 폼의 label 제거 지침이 아님**을 원문도 명시한다.
- **가져올 판단:** 무엇이 먼저 식별돼야 하는지 정한 뒤 제목·값·상태·부가 설명의 무게를 나눈다. 예제 작업 앱 업무 행에서는 제목과 기한/상태를 구별하고 반복되는 설명만 덜어내는 후보가 된다.
- **맞지 않는 경우:** 값 형식만으로 의미를 모르는 데이터, 비슷한 날짜가 여러 개 있는 화면, 폼 label, 스크린리더 이름까지 제거하면 모호해진다. 낮은 위계가 낮은 접근성 대비를 허용하지 않는다.
- **재검증:** 긴 제목, 기한 없음, 낯선 상태를 넣고 구별 가능한지 확인한다. “깔끔해졌다”는 별도의 사용자 평가다. 여백을 최소화하거나 카드를 전부 금지하는 근거로 쓰지 않는다.

## D2. 같은 컨트롤이 다르게 보임 → 먼저 나란히 비교

**Brad Frost.** [Interface Inventory, 2013-07-10](https://bradfrost.com/blog/post/interface-inventory/), [Atomic Design](https://bradfrost.com/blog/post/atomic-web-design/).

- **원글의 행동과 관찰:** 은행 사이트의 여러 버튼을 모아 gradient·화살표·경계 차이를 드러내고 Etsy의 더 일관된 버튼 묶음과 비교했다. 모든 인스턴스보다 서로 다른 처리 방식을 분류하라고 제안한다. Atomic Design에서는 실제 콘텐츠가 들어간 페이지를 통해 구성 요소를 다시 수정한다.
- **가져올 판단:** 동일 역할의 input/button/focus를 상태별로 모아 의도된 차이와 우발적 차이를 나눈다. 공용 컴포넌트와 토큰으로 고치고 실제 dialog·목록 문맥으로 돌아온다. 프로젝트가 채택한 공유 컴포넌트 계약과 함께 적용한다.
- **맞지 않는 경우:** 경고와 일반 입력, 선택과 focus처럼 뜻이 다른 상태까지 하나로 합치지 않는다. 작은 앱에 다섯 계층의 폴더/명명 체계를 강제하거나 전체 design system부터 만들 필요는 없다.
- **재검증:** 공용 변경이 dialog·페이지 양쪽의 오류/disabled/focus와 긴 콘텐츠에서 작동하는지 확인한다. 컴포넌트 단독 예쁜 샘플만으로 완료하지 않는다.

## D3. 폼이 부담스러움 → 질문의 필요와 뜻부터 검토

**Luke Wroblewski.** [What Impacts Web Form Conversion?, 2011-10-04](https://www.lukew.com/ff/1416/what-impacts-web-form-conversion).

- **원글의 사례:** 필드를 줄인 문의 폼, 선택 사항임을 명시한 전화번호, 가입이 필수라는 오해를 줄인 checkout 사례를 소개한다. 페이지를 몇 단계로 나눌지보다 질문을 남길지·미룰지·설명할지 검토하는 데 주목한다. 수치와 수익 효과는 저자가 인용한 사례 보고이며 이 조사에서 원자료를 재검증하지 않았다.
- **가져올 판단:** 각 입력이 현재 결과에 필요한지, 기본값으로 충분한지, 나중에 물어도 되는지 결정한다. 예제 작업 앱의 추가 업무에는 제목/기한 중심, 메모 등 선택 입력은 명확하게 열 수 있는 후보다. 폼을 dialog로 옮기는 것만으로 질문의 부담이 줄었다고 보지 않는다.
- **맞지 않는 경우:** 업무·법적 의무·권한 확인에 필요한 필드는 유지한다. 빈 기본값을 몰래 추측하거나 반복 전문가 입력을 여러 단계로 쪼개면 악화될 수 있다. 공개 사례의 전환율을 우리 앱 예상 효과로 복사하지 않는다.
- **재검증:** 새 항목 추가→저장 결과의 기본값 확인→수정. 선택 입력을 찾을 수 있고 오류/실패 후 입력이 보존되는지 확인한다.

## D4. hover가 떨리거나 목표를 놓침 → 트리거와 효과 분리

**Josh W. Comeau.** [An Interactive Guide to CSS Transitions, 2026-05-05 갱신](https://www.joshwcomeau.com/animation/css-transitions/), [Accessible Animations, 2026-04-29 갱신](https://www.joshwcomeau.com/react/prefers-reduced-motion/).

- **원글의 재현과 수리:** hover 때 요소 자체를 이동시키면 포인터 아래에서 벗어나 hover가 풀리고 다시 들어오는 떨림을 데모로 설명한다. 입력을 받는 button은 두고 자식의 시각 효과를 이동시키는 수리를 제시한다. motion 선호는 사이트가 명시적으로 처리해야 한다고 설명한다.
- **가져올 판단:** 모션 문제를 duration 감각만으로 보지 않고 hit 영역·상태·실제 좌표를 확인한다. 안정된 트리거에서 장식만 움직이는 후보를 고른다. 상호작용의 실제 동작에 맞춰 시작·중간·끝, 중단·반복·역전도 확인한다.
- **맞지 않는 경우:** drag/직접 조작처럼 실제 위치가 변해야 하는 상호작용에는 같은 처방을 강제하지 않는다. 모든 입력에 lift/spring을 추가하거나 예제의 시간을 전역 토큰으로 복사하지 않는다. React hook을 쓰기 위해 스택을 교체하지 않는다.
- **재검증:** 포인터 경계·빠른 재진입·키보드·touch·reduced motion에서 목표와 상태 피드백이 유지되는지 확인한다. GPU 가속이나 성능 수치를 측정 없이 약속하지 않는다.

## D5. 입력 중 오류가 끼어듦 → 필드별로 검증 시점 결정

**Vitaly Friedman.** [A Complete Guide To Live Validation UX, 2022-09-21](https://www.smashingmagazine.com/2022/09/inline-validation-web-forms-ux/).

- **원글의 판단과 사례:** 복잡한 폼에서 사용자가 순서대로만 입력하지 않으므로 blur가 입력 완료라는 보장이 없다고 설명한다. 빈 필드의 성급한 오류, 고친 뒤 남는 오류, 비밀번호 강도처럼 즉시 도움이 되는 피드백을 구분한다. 여러 제품 예시와 다른 연구를 인용한 실무 글이며 모든 설명이 저자의 독립 실험은 아니다.
- **가져올 판단:** “live validation 전부 사용/금지” 대신 필드별 trigger와 복구 시점을 정한다. 제출 전 빈 필드를 벌주지 않고, 이미 지적한 오류가 해결되면 오래 남기지 않는다. 비동기 응답은 입력 revision과 맞춰 판정하는 것이 우리의 구현 제안이다.
- **맞지 않는 경우:** 위험·권한·데이터 무결성 검증은 보존한다. 원글의 validator 우회 제안을 보안 검증 우회로 일반화하지 않는다. 레이블·도움말로 예방할 오류에 알림을 계속 추가하지 않는다.
- **재검증:** 빠른 타이핑·중간 이동·값 수정·느린/역순 응답·서버 실패를 확인한다. 경고가 초안이나 다음 조작을 밀어내지 않고 수정 방법을 알려주는지 본다.

## Hook에서 선택하는 법

`위계/라벨→D1`, `일관성/공유 컴포넌트→D2`, `질문 과다/필수 오해→D3`, `좌표/hover/모션→D4`, `검증/오류/복구→D5`로 필요한 부분만 읽는다. 구조 노출·목록 복귀·overlay 조합은 runtime 레시피 R1–R8과 연결한다.

권위자의 이름을 수정 이유로 끝내지 않는다. `이 과업의 근거 → 원인 → 선택한 개입 → 보존할 장점 → 맞지 않는 조건 → 동일 사례 재검증`을 출력한다. 원글의 사례, 우리 앱에 대한 가설, 실제 실행 결과, 사용자 선호의 상태를 계속 구분한다.
