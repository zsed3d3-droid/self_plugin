# gstack 검토를 개인 UX 기준에 맞추는 범위

개발의 기본 흐름은 gstack이다. 요구·엔지니어링·리뷰·실제 QA의 역할을 연결하고, 작은 명확한 수정에는 반복 승인/전체 계획을 추가하지 않는다. review의 동작·데이터·오류·동시성 관점과 실제 과업 재현은 유지한다.

최신 로컬 gstack의 review/design-checklist에는 특정 글꼴·최소 글자 크기·테두리·모션 속성을 스타일 실패로 보는 규칙도 있다. 그런 저자의 기본값을 보편적 접근성 표준이나 사용자가 채택한 규칙으로 바꾸지 않는다. 예를 들어 system font를 썼다는 이유만으로 교체하거나, 모든 보조 텍스트를 16px로 올리거나, 상태를 설명하는 경계선까지 지우지 않는다. 실제 역할·기기·가독성·DESIGN.md와 사용자의 이유로 판단한다.

확정된 디자인 계약과 기능·접근성 결함, 취향에 관한 휴리스틱은 구분한다. 자동 detector의 hit는 증거 후보이며 사용자 경험의 확정 판정이 아니다. 새 detector를 실행/설치했다고 주장하지 않고, mutable 외부 CLI·온보딩·원격 동기화·과금·배포를 참고 자료 읽기의 자동 권한으로 취급하지 않는다. 실제 gstack 명령을 실행했다면 실행한 범위만 기록한다.

모든 제품과 이전 결과를 보관하라는 현재 사용자 요청이 우선한다. source/reference 유사성을 고치기 위해 과거 결과나 기록을 삭제하지 않고, 다음 iteration의 수정과 이유를 연결한다. 기능 검증·시각 검토·사용자 만족 상태도 계속 나눈다.
