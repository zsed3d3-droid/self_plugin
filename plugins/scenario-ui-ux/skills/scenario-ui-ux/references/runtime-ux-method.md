# 실행 화면의 UX 문제를 고치는 방법

확인일: 2026-10-29. 캡처·브라우저 실행은 기존 live-browser-session 또는 gstack QA를 사용한다. 이 문서는 그 결과로 **무엇이 잘못됐는지 판단하고 어떤 수정을 선택할지** 다룬다. 아래 예제 작업 앱 사례는 진단·재검증 지침이며 현재 구현의 통과 기록이 아니다.

## 1. 증상을 과업과 근거에 연결한다

한 번에 한 과업을 잡는다. 예: “업무 목록을 보다가 기한이 있는 할 일을 추가하고 원래 목록으로 돌아간다.” `답답함`을 바로 padding 값이나 카드 전면 금지로 바꾸지 않는다. 주행동의 경쟁, 정보 순서, 불필요한 질문, 시야 이동, 상태 복구 중 무엇인지 좁힌다.

근거를 다음처럼 구분한다. 동일 기록에 여러 종류가 섞이면 항목별로 표시한다.

| 종류 | 기록할 수 있는 것 | 이 근거만으로 주장할 수 없는 것 |
| --- | --- | --- |
| `user_feedback` | 사용자가 말한 선호·불만과 해당 화면/과업 | 사용자가 실제로 수행한 행동, 다른 사용자의 선호 |
| `user_observation` | 실제 참여자가 수행한 단계, 머문 위치, 발언 | 관찰하지 않은 동기·전체 사용자 집단의 발생률 |
| `agent_task_test` | 에이전트가 실행한 입력, DOM/포커스/응답, assertion 결과 | 실제 사용자 학습성·만족도 검증 |
| `heuristic_review` | 근접성·노출·일관성 등 기준에 따른 예상 문제 | 사용자가 실제로 버튼을 못 찾았다는 사실 |
| `source_review` | 코드·상태 전이·공개 저자의 설명 | 실행 화면에서 재현됐다는 사실 |
| `hypothesis` | 다른 근거로부터 추론한 원인·영향 | 확정 원인·측정한 효과 |

휴리스틱 평가는 잠재 문제를 찾는 검토이며 사용자 연구를 대체하지 않는다. 범위를 과업·사용자·기기로 좁힌다. 실제 참여자가 과업을 수행하는 관찰과 AI의 과업 재현을 구분한다. [NNGroup: 휴리스틱 평가](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/), [사용성 테스트](https://www.nngroup.com/articles/usability-testing-101/).

새 사용자의 관점에서는 각 단계에 네 가지를 묻는다. 지금 해야 할 일을 이해할까, 행동을 찾을까, 이름과 결과를 연결할까, 실행 후 진전을 알까. 답은 평가자의 판단으로 남긴다. 이것이 실제 사용자에게 질문했다는 뜻은 아니다. [NNGroup: Cognitive Walkthroughs](https://www.nngroup.com/articles/cognitive-walkthroughs/).

## 2. 원인에 맞는 수준에서 수리한다

`증상 → 과업 근거 → 원인 가설 → 작은 수정 → 역효과 확인 → 같은 과업 재검증` 순서로 진행한다.

1. **증상:** 위치·상태·행동을 적는다. “어수선하다”보다 “목록을 확인하는 상태에서 생성·가져오기·설정 폼이 함께 펼쳐진다”가 수정 가능하다.
2. **근거:** 기존 캡처/trace를 연결한다. URL/hash, 입력/선택/열린 overlay, viewport·zoom·입력 방식, 데이터 조건과 소스 hash를 함께 남겨 같은 상태를 재현한다. 캡처 파일이 없으면 없는 상태로 기록한다.
3. **진단:** 관찰과 가설을 나눈다. “본문이 아래로 이동했다”는 관찰, “폼 삽입이 layout shift를 만들었다”는 검증할 가설이다. DOM 삽입, scroll/focus 호출, overlay 이벤트, 비동기 재렌더 중 관련 경로를 확인한다. 색 변경으로 상태 전이 문제를 해결했다고 하지 않는다.
4. **수정:** 과업을 막는 원인에 필요한 범위만 바꾼다. 이미 좋아한 영역은 보존한다. 외부 레시피는 [designer-judgment.md](designer-judgment.md)에서 적용 조건과 역효과를 함께 고른다.
5. **재검증:** 같은 초기 상태·과업·기기로 다시 실행하고 전후 근거를 연결한다. 바뀐 입력 hash로 검사하며 기능 assertion, 시각 검토, 사용자 선호를 따로 판정한다. 변경이 없는 전체 앱 검수를 반복하지 않는다.

관찰 가능한 차이가 없는 원인 가설은 확정하지 않는다. 원인이 애매하면 서로 구별할 작은 확인을 먼저 한다. 예: overlay를 열기 전후 `activeElement`와 목록 scroll 위치를 비교해 포커스 이동과 DOM 삽입 영향을 나눈다. 위 과정은 이 플러그인의 운영 방식이며 NNGroup이나 특정 디자이너가 예제 작업 앱에서 검증했다는 주장이 아니다.

## 3. 증상별 수리 레시피

아래는 작업 앱의 과업을 가정한 **조건부 설계 제안**이다. 각 행의 재현 여부와 통과 결과는 실제 실행에서 채운다.

| ID / 증상 | 먼저 확인할 원인 | 수정 후보와 역효과 | 같은 과업으로 확인할 것 |
| --- | --- | --- | --- |
| R1. 모든 기능이 동시에 보임 | 현재 과업과 무관한 생성·설정·후속 작업까지 기본 노출되는가 | 목록/검색을 기본으로 하고 추가·가져오기를 명시적으로 연다. 자주 비교하는 정보까지 숨기면 왕복이 늘어난다. D3 참고 | 처음 진입→주행동 발견→보조 작업 열기→취소. 숨긴 기능의 진입점·이름·현재 범위를 찾을 수 있는지 |
| R2. 인라인 폼을 열자 목록·포커스가 튐 | 폼의 DOM 삽입, 자동 focus, 재렌더가 각각 scroll에 어떤 영향을 주는가 | 짧고 독립적인 추가는 dialog 후보. 연속 대량 입력·목록과 비교하는 편집에는 인라인/옆 영역이 나을 수 있다. dialog가 정답이라고 고정하지 않는다 | 목록 중간에서 열기→입력→취소/저장→목록 복귀. 초안 정책, scroll·필터·포커스 복구, 저장 실패 후 입력 보존 |
| R3. dialog 안 메뉴에서 Escape가 둘 다 닫음 | 열린 overlay 계층과 key/cancel 이벤트가 부모까지 처리되는가 | 가장 안쪽 열린 팝업이 닫기 동작을 소비하고 트리거로 복귀하도록 구현. 닫기 기능 자체를 없애거나 모든 키 전파를 막지 않는다 | 메뉴 열기→Escape는 메뉴만 닫음→다음 Escape는 dialog 닫음. Enter가 배경 폼을 제출하지 않는지, 반복 열기·포커스 복귀 |
| R4. 목록·상세가 함께 길게 늘어짐 / 뒤로 가면 맥락 유실 | 목록→상세→복귀 상태가 정의됐는가, 화면 크기에 따라 의도가 달라지는가 | 선택 시 상세 중심, 명확한 목록 복귀와 위치 보존. 반복 비교가 핵심이면 master-detail 병렬 구성을 유지할 수 있다 | 회의 선택→상세→목록/브라우저 뒤로. 필터·선택·scroll, 새로고침/직접 링크, 좁은 화면에서 중복 헤딩/빈 상세 |
| R5. 카드 속 카드, 모든 텍스트가 같은 무게 | 카드 경계가 실제 독립 선택·소유권을 나타내는가, 제목·값·상태의 위계가 있는가 | 먼저 제목·정렬·근접성·구분선으로 묶고 불필요한 경계만 제거. 비교 단위나 클릭 범위가 흐려지면 경계를 유지. D1 참고 | 긴 한영 제목·기한 없음·서로 다른 상태에서 제목/기한/상태를 구별. 간격을 줄여 내용이 붙는 부작용 확인 |
| R6. 단순하게 만들다가 기본 정보가 사라짐 | 노출을 줄인 대상이 과업 판단에 필요한 값인가 | 업무 제목·상태·기한, 회의 출처, 현재 검색 범위처럼 필요한 정보를 복원. 모든 메타데이터를 기본 화면에 올리지는 않는다 | 목록에서 상태/기한 판단, 빈 결과/오류/로딩 구별, 생성 기본값이 저장 결과와 일치하는지 |
| R7. 같은 입력인데 focus 모양·동작이 제각각 | 의미가 같은 컴포넌트가 다른 CSS·wrapper focus를 갖는가 | 공용 토큰/컴포넌트로 정리하고 이중 ring을 없앤다. 경고·선택·키보드 focus를 한 상태로 합치지 않는다. D2 참고 | 동일 컨트롤의 기본/키보드/선택/오류, dialog 내부·외부, 좁은 화면에서 경계 잘림 |
| R8. 입력 중 오류가 번쩍이거나 고친 값도 오류로 남음 | 입력 완료를 성급히 가정하는가, 오래된 비동기 응답이 최신 값을 덮는가 | 필드별 검증 시점·응답 순서를 정하고 실패 후 초안 유지. 보안·정확성 검증을 완화하지 않는다. D5 참고 | 일부 입력→다른 필드→수정→느린 응답→제출. 조기 오류·stale 오류·이중 제출·입력 유실 |

R3의 overlay 계층 순서는 이 앱의 조합 계약이다. W3C APG는 dialog 안의 Tab 순환·Escape·적절한 초기/복귀 focus와 메뉴의 Escape/트리거 복귀를 설명한다. 실제 컨트롤이 선택 listbox인지 action menu인지 확인해 해당 패턴을 선택한다. 달력에는 별도의 grid/date-picker 상호작용이 필요하다. native select를 외형 때문에 custom으로 바꾸면 기존 키보드·이름·상태 계약도 책임진다. [APG Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [Menu Button](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/), [Menu](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/), [Date Picker 예시](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/).

근접성은 관련 항목을 가깝게, 다른 묶음을 구별하게 만드는 판단 근거다. 고정된 4/8/16px나 무조건 무경계 UI를 증명하는 법칙이 아니다. responsive 전환 후에도 실제 의미 묶음이 유지되는지 확인한다. [NNGroup: Proximity](https://www.nngroup.com/articles/gestalt-proximity/).

## 4. 작은 수정에서도 보존할 접근성

| 확인 | 적용 기준 |
| --- | --- |
| 키보드 | 포인터 없이 기능을 수행할 수 있어야 한다. 경로 자체에 의존하는 입력 등 기준의 예외는 구분한다. [WCAG 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) |
| focus 순서·표시 | 의미와 조작을 보존하는 순서, 키보드 focus를 알 수 있는 표시를 확인한다. 특정 ring 색/두께가 이 두 기준의 유일한 해법은 아니다. [2.4.3](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html), [2.4.7](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) |
| 가려짐 | 고정 헤더·팝업 등 작성자 콘텐츠가 focus 받은 항목을 완전히 가리지 않게 한다. AA의 최소 기준과 프로젝트가 원하는 더 넓은 가시성을 구분한다. [2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) |
| reflow | 세로 콘텐츠는 320 CSS px 상당 너비에서 정보·기능 손실과 양방향 scroll을 점검한다. 의미상 2차원 배치가 필요한 표/지도 등의 예외는 해당 영역에 적용한다. 데스크톱 1280px에서 400% zoom한 조건도 확인한다. [1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) |

Understanding/APG 문서는 설명·구현 지침이다. 규범 기준은 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)를 따른다. 일부 viewport와 자동 검사 통과만으로 WCAG 전체 준수를 선언하지 않는다.

## 5. Hook reviewer에 넘길 최소 계약

[JSON 예시](../templates/runtime-ux-evidence.example.json)는 **실행하지 않은 예시**다. 캡처를 다시 만드는 서비스나 별도 DB를 추가하지 않는다. 기존 Hook의 hash·예산·실행 gate와 연결할 증거 파일로 사용한다.

reviewer는 현재 변경과 해당 레시피만 읽고 다음 형식으로 피드백한다.

> 과업/상태와 근거 위치를 먼저 제시한다. 관찰과 원인 가설을 분리한다. 이번 과업의 사용자 영향, 원인을 가를 확인, 가장 작은 수정, 보존할 기능/선호, 역효과와 동일 과업 재검증을 적는다. 실제 근거가 없으면 미검증으로 남긴다. 일반적 취향·색상 처방·전면 재설계를 자동 위반으로 만들지 않는다.

- `findings[].basis`는 위 여섯 종류 중 하나다. 원인에는 `hypothesis|confirmed|unresolved`를 표시하고 confirmed에는 코드/trace/실행 근거를 연결한다. 심각도는 `blocked|recoverable|friction|preference`로 구분하되 사용자 발생률·시간 절감은 측정 없이는 쓰지 않는다.
- assertion은 기대값/실제값/상태/근거를 갖는다. `not_run`·근거 없음·이전 입력 hash의 통과를 현재 성공으로 바꾸지 않는다. 전체 통과는 실제 assertion 통과와 해당 전후 화면 검토가 모두 기록됐을 때만 가능하다. 이 예시는 별도의 실행 검증기를 구현하지 않는다.
- 기능 검증, 시각 검토, 사용자 선호 평가는 별도 상태다. 사용자 재평가가 없으면 `not_evaluated`로 둔다. 자동 검수는 사용자의 승인을 만들어내지 않는다.
- 사용자 피드백은 원문/이유·화면/영역·과업/기기·수정·결과를 기존 개인화 기록에 연결한다. 특정 화면의 구성·색상 선호를 다른 프로젝트의 전역 취향으로 자동 승격하지 않는다.

## 실제 요소에 적용되는 형태도 확인한다

토큰 값이 올바르다는 사실은 CSS selector가 실제 요소를 덮는다는 증거가 아니다. Cadence에서 내보내기 버튼을 의미에 맞는 `<a download>`로 바꾼 뒤 같은 primary class를 유지했지만, radius 규칙이 button에만 걸려 링크는 0px·이웃 버튼은 8px이 됐다. 실제 캡처와 계산된 스타일에서 확인했으며 키보드 도달과 3px focus outline은 이미 정상이라 보존한다. 수리는 프로젝트의 공유 action class에 같은 형태를 적용하는 범위다. 링크를 버튼으로 되돌리거나 다른 브랜드·도형까지 모두 둥글게 만들지 않는다.

이 관찰의 근거는 실험실 `ux-lab/products/003-cadence/verification/root-control-geometry-1793212205567/observations.json`이다. 이후 `ux-lab/products/003-cadence/verification/root-round4-1793213875208/checks.json`에서 세 화면 폭의 링크·버튼 radius가 모두8px이고, 현재 파일 다운로드가 새 작업을 만들지 않는 것을 확인했다. 사용자 취향 재평가와는 별도다. 의미 요소·상태·variant가 바뀌는 경우 실제 적용된 스타일과 같은 과업을 확인한다. 불필요한 전면 재설계·새 스타일 테스트 묶음·전체 suite 반복을 추가하지 않는다. source 선언 검사와 실제 적용·시각 판단의 한계를 구분한다.


## 파일을 가져가는 과업이면 출력물까지 이어서 확인한다

Offcut은 root overflow가 0이어도 고정 SVG 안의 80자 제목·재료가 잘렸다. SVG를 직접 렌더하고 각 글자의 경계를 viewBox와 비교해서 확인했다. 원문을 자르지 않고 줄 수에 따라 출력 높이를 늘린 새 recipe는 같은 v1 입력으로 통과했고, 이전 잘린 파일의 SHA는 유지했다. 근거: `ux-lab/products/004-offcut/verification/root-audit/export-observe-1793216614130/`와 `export-wrap-1793216784650/`.

인쇄가 실제 다음 행동이면 브라우저 화면뿐 아니라 해당 용지로 출력한 페이지도 본다. 같은 제품에서 두 번째 재고만 따로 렌더하며 SVG의 번호가 01로 초기화됐다. A4의 바깥 제목은 재고2인데 그림은01이었다. 전역 재고 번호를 전달한 같은 두 재고 출력은 페이지별01/02로 맞아졌다. 근거: 같은 root-audit 아래 `print-pdf-1793216851021/`와 `print-final-1793217176804/`. 물리 프린터 검증이나 사용자 만족을 뜻하지 않는다.

조건부 확인: 현재 과업의 원본·version·recipe·전역 항목 ID가 파일까지 이어지는가, 허용된 긴 한영 입력이 파일 내부 경계에 들어가는가, 해당 출력의 실제 페이지에 누락·중복 식별이 있는가. 단순 웹 텍스트 수정에 PDF 검사를 강제하지 않는다. 기존 불변 파일은 새 코드로 덮지 않고 새 출력으로 수리한다. 사용자가 파일 형식을 배워야 다음 행동을 찾는다면 목적을 드러내는 행동명도 검토하되, 실제 발견성 향상은 사용자 관찰 없이 확정하지 않는다.


## 정밀 조작은 표시·클릭 영역·데이터 경계를 나눠 확인한다

Looproom의 17초 음원에서 3–3.1초를 지정하자 A/B 손잡이가 27.92px 겹쳤다. 각 손잡이의 크기는 30×26px였지만 A 가운데를 누르면 B가 선택되고 범위 오류가 났다. 컨트롤의 선언 크기만으로 실제 조작 가능성을 판단할 수 없었다. 근거: `ux-lab/products/006-looproom/verification/root-ui/narrow-markers-1793225545572/`.

실제 시간 경계선은 캔버스의 정확한 위치에 두고, 겹칠 때만 표시 손잡이를 위아래로 나눴다. 가장자리에서 표시를 안쪽으로 옮겼다는 이유로 데이터 값까지 바뀌지 않도록, 누른 시점의 값과 실제 드래그 거리를 사용했다. 같은 음원의 중앙·시작·끝에서 두 클릭 대상, 값이 변하지 않는 단순 클릭, 실제 드래그를 다시 확인했다. 7개 조건·6회 드래그와 경계 픽셀 확인은 `narrow-markers-fixed-1793225855709/report.json`에 있다.

타임라인·지도·범위 선택처럼 정밀 조작이 필요한 과업에서 적용할 조건부 확인이다. 실제 최소 구간·확대 상태·가장자리에서 가려짐과 hit target을 검사하고, 포인터·키보드·숫자 입력이 같은 데이터를 조작하는지 확인한다. 이 사례를 모든 버튼의 크기·모양이나 간격에 대한 전역 처방으로 바꾸지 않는다. 기능 통과와 사용자 만족은 별도다.


## 입력 직후 이어지는 첫 조작도 같은 경로로 확인한다

Cueframe에서 시간 입력을 바꾼 뒤 바로 옆 ‘전체 보기’를 누르면 첫 클릭이 사라졌다. 실제 trace는 기존 버튼의 pointerdown → 입력 blur/change에서 인용 DOM 교체 → 새 버튼의 pointerup 순서였다. 단순히 버튼만 누르는 검사는 통과했다. 같은 값에는 다시 렌더하지 않고, 시간 입력과 무관한 인용 DOM을 해당 원본·cue·본문이 같은 동안 유지해 수리했다. 같은 80줄·159자 본문으로 두 시각을 입력한 직후 한 번의 포인터 클릭이 열리는지 390/320px에서 확인했다. 근거: `ux-lab/products/007-cueframe/verification/root-ui/fulltext-click-1793231021497/report.json`과 `fulltext-final-1793231385688/report.json`.

조건부 확인은 입력→blur/검증→바로 다음 행동의 실제 이벤트 순서다. DOM을 모두 고정하거나 유효한 변경을 무시하는 전역 규칙으로 만들지 않는다. 바뀐 원본·cue·본문은 여전히 갱신해야 한다. 포인터 재시도나 테스트의 강제 클릭으로 첫 조작 실패를 숨기지 않는다.

같은 과업에서 문자 수만으로 축약 여부를 정해 159자가 80줄의 표 행을 만들었다. 표시 영역은 실제 줄·높이로 제한하되 전체 원문은 별도 읽기 경로에 보존했다. 전체 읽기의 끝에서도 닫기를 찾을 수 있게 본문만 스크롤하고, 닫으면 원래 편집값·초점으로 돌아왔다. 이는 긴 본문을 읽는 과업의 확인 조건이며, 모든 콘텐츠를 잘라 표시하거나 모든 dialog에 고정 높이를 강제하는 규칙이 아니다. 한 장의 과거 캡처가 같은 이름에 덮인 보존 실수는 별도 한계로 기록했고 새 캡처를 원본 복구로 취급하지 않았다.
