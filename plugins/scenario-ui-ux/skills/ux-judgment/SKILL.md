# UX Judgment

구현된 화면의 문제를 `과업 근거 → 원인 질문 → 작은 수정 → 역효과 → 같은 사례 검증`으로 해결한다. gstack과 scenario-ui-ux의 개발 흐름 안에서 필요한 판단 자료로 사용한다. 별도 캡처·승인·배포 절차를 만들지 않는다.

## 먼저 보존한다

사용자의 현재 요청과 연결된 비공개 프로젝트 판단의 **실제 이유**가 우선이다. 개인 판단 원문은 이 배포에 포함하지 않는다. 범위가 맞는 채택된 개인 규칙·프로젝트 계약을 읽고 좋아한 영역을 보존한다. [개인 UI 판단](../scenario-ui-ux/references/personal-ui.md)을 참고한다. 특정 화면에서 받은 긍정 평가를 다른 제품의 전역 취향으로 확대하지 않는다. 기능·보안·접근성과 서비스 컨테이너 원칙, 승인된 MLX 호스트 예외를 유지한다.

라이브러리의 20개 레시피는 모두 **새 후보**다. 저자의 주장과 우리의 구현 가설을 구분한다. 이를 사용자가 채택한 규칙, 실행한 실험, 만족한 결과로 기록하지 않는다.

## 증상과 과업으로 좁힌다

한 과업과 문제가 발생한 상태를 적고 후보를 찾는다. [색인](references/author-index.md)은 저자·증상별 빠른 안내이고, [라이브러리](references/author-library.json)는 원문 URL·게시/확인일·근거 종류·한계·실험을 보존한다.

철학을 실제 약속으로 옮길 때는 [practice-contracts.md](references/practice-contracts.md)의 해당 행만 참고한다. 실제 Proofline의 초안 수리가 새 좌표 회귀를 만든 반례도 함께 읽고, 원칙의 이름만으로 수리를 정당화하지 않는다.

```sh
python3 scripts/select-judgment.py --problem "모든 폼이 동시 노출되어 답답하다" --task "업무 목록에서 할 일 추가" --limit 3
python3 scripts/select-judgment.py --problem "달력에서 Escape를 누르면 부모 창도 닫힌다" --task "keyboard controls" --format text
python3 scripts/select-judgment.py --tag tone-mismatch --task "오류 문구" --limit 2
```

이 스크립트는 **오프라인 태그·명시적 동의어·키워드 검색**이다. 의미검색, 인과 진단, 실제 화면 검토를 수행하지 않는다. 매칭 이유를 함께 보고 이번 과업에 맞는 한두 개만 고른다. 점수는 유명도·품질·사용자 선호의 점수가 아니다. 무관한 입력은 빈 결과로 반환한다. 이를 이유로 10명의 규칙을 모두 로드하거나 검색 서비스·모델을 추가하지 않는다.

좌표/선택과 덮어쓰기/불일치가 함께 나오거나 `mental model`·`state-intent-mismatch`처럼 명시된 경우 구체적인 상태/의도 후보를 일반 `feedback`보다 먼저 찾는다. 이는 공개된 어휘 분류이며 의미 추론이 아니다. problem/task에 같은 일반 태그가 반복돼도 한 신호로 계산한다. 위치라는 말만으로 상태 버그를 확정하지 않는다.

## 원인에 맞는 작은 수리를 고른다

1. **근거:** 실제 사용자 발언/관찰, 에이전트 과업 테스트, 휴리스틱 검토, 코드 검토, 가설을 구분한다. 기존 캡처·trace에 과업/상태·기기·입력 hash를 연결한다. AI 테스트를 실사용자 연구라고 부르지 않는다.
2. **진단:** 후보의 `diagnosis_question_ko`로 원인을 좁힌다. 버튼이 안 보이는가, 기능을 몰랐는가, 전달이 끊겼는가, 오류 후 복구할 수 없는가? 캡처만으로 사용자의 생각과 인과를 확정하지 않는다.
3. **수리:** `small_repair_ko` 중 지금 원인을 고치는 범위만 적용한다. `preserve_ko`, `tradeoffs_ko`, `countercases_ko`를 함께 읽는다. 모든 질문을 모달로 옮기거나 모든 카드·장식·모션을 없애지 않는다.
4. **검증:** `same_case_verification`에 따라 같은 데이터·과업·초기 상태·기기로 재실행한다. 기능 assertion과 전후 화면을 확인하고 변경과 연결된 회귀를 본다. 명확한 국소 수정에 긴 철학 설명·대안 세 개·반복 승인을 강제하지 않는다.
5. **평가:** 기능/시각 검토 결과와 사용자 선호를 별도로 남긴다. 사용자 평가가 없으면 미평가다. 해당 화면의 판단을 다른 제품에 자동 승격하지 않는다.

메뉴·달력은 역할에 맞는 키보드·focus·취소/복귀 계약을 유지한다. 모션은 시작·중간·끝과 중단/반복, reduced motion을 확인한다. 요약·담당자 추출은 원문과 불확실성을 보존한다. [실행 UX 수리 방법](../scenario-ui-ux/references/runtime-ux-method.md)에 관련 조합 사례가 있다.

## 경험을 다음 판단의 근거로 남긴다

[경험 로그 예시](templates/experience.example.json)에 아래 필드를 기록한다. 기존 프로젝트의 경험 저장 경로를 사용하며 이 스킬 때문에 DB·서비스·자동 수집을 추가하지 않는다.

| 필드 | 내용 |
| --- | --- |
| `product`, `cycle` | 제품/화면/과업 범위, 요청·반복 ID, 입력 hash |
| `symptom`, `cause` | 기대/관찰, 사용자 원문 참조, 원인 가설·확인 상태 |
| `change` | 바꾼 것, 보존한 장점, 예상 역효과 |
| `evidence` | 실제 캡처/trace/assertion/발언의 종류와 위치 |
| `actual_results` | 같은 사례의 기능·시각·선호 결과와 실제 측정 |
| `limitations`, `source_recipes`, `status` | 미확인 범위, 사용한 후보 ID, 실행 상태 |

실제 `evidence` 항목에는 `id`, `kind`, `locator`, `observed_at`을 둔다. `kind`는 `user_feedback|user_observation|agent_task_test|heuristic_review|source_review|hypothesis`이며 위치만 가진 출처 설명과 실제 관찰을 혼동하지 않는다. 측정 항목에는 이름·기대/실제 값·근거 ID를 연결한다. 원인 `confirmed`에는 확인 근거가 필요하다.

예시는 `not_run`이다. 근거가 없으면 null/빈 배열·미실행을 유지한다. 실제 결과가 있으면 그 결과와 한계부터 기록하고, 사용자 채택/거절 이유를 해당 범위에 연결한다. 반례나 후속 불만은 지침을 좁힐 근거이며 무조건 더 많은 규칙을 추가할 이유가 아니다.
