아래는 원문들을 현재 개발 흐름에 맞춰 조합한 운영 제안이다. 저자들이 공동으로 정한 철학이나 사용자가 새로 채택한 20개 규칙이 아니다. 현재 사용자 요구와 연결된 비공개 프로젝트 판단의 이유가 우선하며, 해당 과업에 필요한 행만 쓴다.

## 실제로 생긴 반례: Proofline

처음에는 Escape 후 입력 유실을 고치려고 버전별 초안을 보존했다. 그러나 위치가 다른 댓글까지 같은 key로 묶여 새로 선택한 좌표를 이전 초안이 덮었다. 보존이라는 원칙만으로 좋은 UX가 되지 않았다. 의도/위치/버전의 범위를 나누고, 새 작성과 이전 초안 재개를 명시적으로 구별한 뒤 같은 좌표 변경 과업으로 재검증했다.

저장 중에는 버튼만 잠가도 새 입력과 재오픈을 통한 중복 제출이 남았다. 같은 요청의 처리 결과를 보존하고, 진행 중 폼 상태·제한 시간·늦은 결과의 소유권을 함께 정했다. 이 사례가 모든 폼을 항상 잠그거나 영구 저장하는 이유는 아니다. 긴 작업에는 취소/백그라운드 진행이 나을 수 있고 민감한 입력에는 별도 보존 정책이 필요하다.

실험 결과는 `ux-lab/products/001-proofline/CHANGELOG.md`와 독립 검증 기록에 있다. 이는 실제 에이전트 과업 테스트와 코드 수리 사례이며 사용자 만족 연구가 아니다. 이후 제품에서도 맞는 범위에만 회수하고 반대 결과가 나오면 해석을 줄인다.
