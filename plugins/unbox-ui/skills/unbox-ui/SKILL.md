# Unbox UI — 카드카드네모병 탈출

목표는 카드 수를 줄이는 것 자체가 아니라, 핵심 정보·정보 관계·행동을 더 빨리 읽히게 하는 것이다. 필요한 카드와 컨트롤은 남긴다.

## 범위부터 정하기

- 리뷰·점검 요청은 근거와 대안만 제시하고 파일을 변경하지 않는다. 수정·구현 요청이면 지정한 화면/컴포넌트 안에서 적용하고 검증한다.
- 실제 화면과 관련 소스, 공유 컴포넌트의 사용처, 디자인 토큰을 먼저 확인한다. 스크린샷만 있으면 시각적 추정과 확인된 동작을 구분한다. 박스 모양만 보고 클릭 가능하다고 단정하지 않는다.
- 신규 화면은 카드 그리드부터 만들지 말고, 사용자의 첫 과업과 제목→핵심 내용→보조정보→행동의 읽기 순서부터 정한다.
- 기존 디자인 시스템·브랜드·정보 밀도를 보존한다. 이 스킬만으로 색상/폰트 교체, 전체 앱 재설계, 새 의존성, 애니메이션, 배포를 추가하지 않는다.

## 1. 박스의 역할 판별하기

레이아웃용 `div`, 의미상 `section`, 실제 시각적 카드, 입력 컨트롤의 경계를 구분한다. DOM 중첩 자체가 문제는 아니다.

각 시각적 박스에 아래 질문을 적용한다.

- 영역 자체가 클릭 가능한가? 내부 링크 하나만 있는 것은 전체 영역의 클릭성과 다르다.
- 다른 정보와 독립된 객체인가? 예: 별도 목적지/작업/소유자를 가진 항목.
- 사용자가 선택해야 하는 옵션이며 선택·비선택 상태 구분이 필요한가?
- 중요한 CTA를 배경에서 분리해야 하는가?
- 같은 화면에서 실제로 우선순위를 높여야 하는가?

하나라도 YES면 박스를 유지할 수 있다. 반드시 박스를 쓰라는 뜻은 아니다. 전부 NO면 제거/대체 후보로 둔다. 정보 삭제와 시각적 경계 제거를 혼동하지 않는다.

다음은 재검토 신호이지 자동 삭제 조건이 아니다: 카드 안 카드, 모든 정보의 같은 크기 네모, 섹션마다 자동 박스, 내용보다 강한 테두리/배경, 축소 시 네모만 보임, 관계보다 칸 나누기가 먼저 느껴짐.

## 2. 더 가벼운 구분 방식 선택하기

주어진 참고 이미지의 여섯 원칙을 아래처럼 적용한다. 한 화면에 모두 적용할 필요는 없다.

| 방식 | 적용할 때 | 주의 |
| --- | --- | --- |
| 여백으로 묶기 | 관련 제목·설명·행동을 가까이, 다른 그룹은 더 멀리 배치 | 그룹 간 간격을 내부 간격보다 크게. 약 2배는 시작 예시일 뿐 고정 규격이 아니다. 지나친 여백으로 행동을 떼어 놓지 않는다. |
| 정렬로 묶기 | 제목·본문·메타정보의 시작점과 기준선을 통일 | 긴 한글·줄바꿈·좁은 화면에서도 관계가 유지되어야 한다. |
| 배경 차이 주기 | 큰 기능 영역의 구분이 여백만으로 불충분 | 기존 surface 토큰의 명도 차이를 사용한다. 모든 행을 또 다른 배경 박스로 만들지 않는다. |
| 선 하나로 나누기 | FAQ·설정·반복 목록에서 항목 경계가 필요 | 행 사이 separator부터 고려한다. 독립된 카드나 선택 옵션을 무조건 목록으로 바꾸지 않는다. |
| 타이포에 위계 주기 | 제목·핵심 값·본문·보조정보가 모두 같은 무게 | 기존 토큰으로 주/본문/보조 수준을 구분한다. 세 수준은 출발점이며 글자 축소·저대비로 해결하지 않는다. |
| 라벨로 성격 표시 | 기간·역할·기여도 등 반복 정보의 종류 식별 | 짧은 텍스트 라벨을 우선한다. 필요한 상태만 작은 배지로 표시하며 라벨마다 색상·아이콘·pill을 붙이지 않는다. |

## 3. 큰 구조를 확인하고 안쪽 장식부터 줄이기

1. 가장 큰 박스의 역할과 읽기 순서를 확인한다. 외곽 그룹이 필요한 경우 유지한다.
2. 같은 역할을 중복하는 내부 카드부터 줄인다. DOM/컴포넌트가 레이아웃·접근성·상태를 담당하면 시각적 장식만 제거한다.
3. 배경·테두리·그림자·라운드가 동시에 필요한지 확인하고 중복 강조를 덜어낸다. 단순한 그룹은 여백/정렬부터, 부족할 때 한 가지 경계를 더한다.
4. 제목·설명·보조정보·행동의 순서와 간격을 재조정한다. 주 행동은 관련 정보 가까이에 두고 보조 행동과 구별한다.
5. 여전히 모호한 독립 객체·선택 옵션·중요 경고에는 필요한 표면/경계를 다시 넣고 그 이유를 설명한다.

반복 패턴의 기본 대안:

| 기존 | 대안 |
| --- | --- |
| 섹션 카드 안에 정보 카드 4~6개 | 열린 섹션 + 정렬된 정보 그룹, 또는 외곽 표면 하나 + 내부 행 |
| 지표마다 박스와 아이콘 | 박스 없는 지표 그룹 + 값의 위계 + 단위/기간 라벨 |
| 기간/역할/툴/기여도 각각 카드 | `dl`의 라벨/값 또는 인라인 보조정보 |
| 설명 문장까지 내부 배경 박스 | 제목 가까운 일반 본문. 실제 경고/예외만 별도 강조 |
| FAQ·설정 목록을 개별 카드화 | 목록/접기 컨트롤 + 필요한 행 구분선 |
| 비교용 데이터를 같은 크기 카드로 반복 | 행·열 비교가 과업이면 실제 `table`; 독립 객체 탐색이면 카드를 유지할 수 있음 |
| 복합 뷰어(PDF/Canvas/차트/지도)를 카드 안 카드·패딩으로 다중 감싸기 | 외곽 장식 박스를 걷어내고 단일 기능적 뷰어 표면으로 평탄화(Flatten)하여 실측 가용 폭 극대화 |
| 출처/참조/태그 배지 목록을 카드 박스로 감싸거나 가로로 길게 늘어놓기 | 기본 1개 단일 배지 노출 + 소형 '+' 토글 버튼으로 세로 전개. 별도 감싸는 카드 박스 없이 2px 간격의 정렬선 맞춤 플랫 스택(`flex-direction: column; gap: 2px`)으로 경량화 |
| 반복되는 목록·설정·사용자 권한을 개별 둥근 카드 박스로 파편화 | 단일 데이터 테이블의 줄(Row) 형태로 전환하고, 1px 구분선(`border-bottom`)과 전용 컬럼(부서/소속 등 독립 열)을 두어 정보 밀도 극대화 |

`border-driven` 스타일도 모든 섹션에 네 면의 테두리를 요구하는 뜻은 아니다. 기존 컴포넌트의 허용 범위 안에서 구분선이나 열린 그룹을 사용한다. 공유 Card의 전역 스타일 변경은 사용처 전체에 같은 개선이 필요할 때만 한다.

### 3-1. 관리·워크벤치 화면의 위계와 배치

목록·상세·설정 탭이 반복되는 관리 화면에서 AI가 자주 놓치는 구조 문제다. 박스를 줄인 뒤에도 아래 항목이 남아 있으면 위계가 깨진 것으로 본다.

| 점검 | 흔한 실수 | 기준 | 확인 방법 |
| --- | --- | --- | --- |
| 하나의 시작선 | 영역마다 `padding`을 따로 지정해 상단바·제목·탭·필터·표 첫 글자의 왼쪽 시작점이 수 px~수십 px씩 어긋남 | 한 화면의 주요 행은 하나의 gutter 토큰을 공유한다. 행 선택 강조선 같은 장식은 시작선 바깥(음수 보정 또는 inset)으로 둔다 | 각 행 첫 글자의 `getBoundingClientRect().left`를 비교해 1px 이내 |
| 제목과 내비게이션 일치 | 페이지 제목이 메뉴 이름과 다르거나, 하위 탭을 바꾸면 제목이 탭 이름으로 바뀜 | 페이지 제목은 현재 메뉴 이름으로 고정하고, 탭은 제목 아래의 하위 위치로만 표시한다 | 모든 메뉴·탭을 순회하며 `h1`과 활성 메뉴 텍스트 비교 |
| 안내 문구 한 곳 | 같은 설명을 하단 메타 줄·도움말·접힘 영역·빈 화면에 반복 | 설명은 가장 가까운 한 곳(도움말 또는 해당 탭)에만 둔다. 화면 하단에 별도 메타 정보 줄을 만들지 않는다 | 화면 텍스트에서 같은 문장이 두 번 이상 나오는지 검색 |
| 상세는 라벨/값 묶음 | 상세 패널에 원본 키(`created_at`, `run_id`)와 JSON을 그대로 나열 | `종류 → 제목 → 상태·ID → 묶음별 dl → 행동` 순서. 원본 데이터는 맨 아래 접힘 영역 하나로 제한한다 | 상세 패널에서 snake_case 키나 `{`가 본문에 노출되는지 확인 |
| 성격이 다른 기록 분리 | 사람이 만든 항목과 서비스·자동 생성 기록을 한 목록에 섞어 같은 제목 행이 수백 개 반복 | 생성 주체나 종류가 다르면 목록 위 segmented 필터로 나누고, 기본값은 사람이 다루는 쪽으로 둔다. 목록 이름은 실제 데이터 범위와 일치해야 한다 | 가장 데이터가 많은 계정·프로젝트로 목록을 열어 동일 제목 반복 여부 확인 |
| 떠 있는 하단 영역 | 고정 `min-height` 때문에 메타 줄·푸터가 콘텐츠가 짧을 때 화면 중간에 뜸 | 높이를 고정해 영역을 띄우지 않는다. 하단 정보는 콘텐츠 흐름의 끝에 둔다 | 데이터 0건 상태로 캡처 |

## 4. 기능과 접근성 보호하기

- 입력 영역, 선택 상태, 포커스 표시, 오류/경고, 드래그 대상, 모달/팝오버 경계를 장식 카드와 구분한다. 필요한 식별성과 대비를 없애지 않는다.
- **인라인 참조·출처 배지 스택의 카드화 방지 (Compact Inline Badge Stack & Unboxed Vertical Expansion)**: 본문이나 문단 끝에 인라인으로 붙는 출처/참조/태그 목록은 본문 줄바꿈을 유발하는 무분별한 가로 나열이나, 배지들을 감싸는 불필요한 카드 테두리 상자를 금지한다. 기본 상태에서는 가장 신뢰도 높은 첫 번째 배지 1개만 단일 노출하고, 2개 이상일 때는 소형 인라인 원형 '+' 토글 버튼(`aria-label="출처 N개 더보기"`)을 제공한다. 확장 시에도 감싸는 외곽 카드 상자를 추가하지 않고, 첫 번째 배지의 좌측 시작선에 맞춰 아래로 세로 전개(`flex-direction: column`)하며 항목 간 간격은 최소 2px(`gap: 2px`)로 절제하여 텍스트 흐름을 깨뜨리지 않는다.
- 카드를 제거하고 앵커드 팝오버나 미니멀 오버레이로 전환할 때, 팝오버 DOM을 트리거 컨테이너(사이드바, 카드, 테이블 셀 등) 내부에 중첩하지 않고 반드시 `document.body` 최상단에 마운트(React `createPortal`, Vanilla `appendChild`)하며, 팝오버 위치는 항상 오픈을 트리거한 버튼의 `getBoundingClientRect()` 뷰포트 상대 좌표에 동적으로 앵커링(Smart Flip 포함)하여 부모의 `overflow` 클리핑이나 쌓임 맥락(Stacking Context) 갇힘을 방지한다.
- 고정 종횡비 픽셀 비트맵과 절대좌표 DOM 오버레이가 결합된 복합 뷰어(PDF.js, Canvas, 인터랙티브 차트 등)는 텍스트 레이어 및 컨트롤과의 좌표 일치를 보호하기 위해 **단일 1px 보더의 기능적 표면(Functional Surface)**으로 보존한다. 단, 뷰어를 감싸는 모든 조상 그리드/플렉스 레이아웃에 `min-width: 0; max-width: 100%; box-sizing: border-box;` (Confinement Armor)를 부여하여, 좁은 화면에서 상위 카드가 찢어지거나 가로 스크롤이 폭발하지 않도록 격리한다.
- 정적 정보는 버튼 같은 hover·pointer·chevron을 남기지 않는다. 실제 행동의 발견 가능성, 충분한 클릭 영역과 키보드 조작은 유지한다.
- 이동은 목적지가 있는 네이티브 링크, 동작은 버튼을 우선한다. 이 변경이 필요할 때 기존 인증·로그인 복귀·권한·사용 기록 경로를 보존하며 직접 URL로 우회하지 않는다.
- 카드 전체를 링크로 만들 때 내부 버튼/링크를 중첩하지 않는다. 복수 행동이 있으면 비인터랙티브 컨테이너와 개별 컨트롤로 구분한다.
- **대화형 요소 중첩 절대 금지 (No Interactive Descendant Nesting)**: `<button>`, `<a>`, `<summary>`, `tabindex="0"` 컨트롤 내부에 또 다른 `<button>`, `tabindex="0"`, `onClick.stopPropagation()`을 가진 인라인 요소(예: 안내 물음표 아이콘)를 절대 중첩하지 않는다. 이는 W3C HTML 명세 위반이자 focus/blur 이벤트 충돌로 상위 팝오버·카드의 튕김(플리커) 현상을 초래한다. 안내 툴팁은 마우스 호버 전용 CSS 오버레이(`pointer-events: none` 팝업) 또는 상위 버튼과 대등한 형제(Sibling) 컨트롤로 완전히 분리한다.
- **복합 입력 래퍼의 중첩 테두리·이중 포커스 박스 방지 (No Double-Focus Stroke in Compound Inputs)**: 전송 버튼이나 첨부 아이콘과 함께 묶인 복합 입력창 래퍼(`.composer-row`, `.input-container`, `.search-bar`)는 외곽 단 1곳에서만 포커스 상태(`:focus-within`)를 표현해야 한다. 내부 에디터(`contenteditable`, `<input>`, `<textarea>`)에 독립적인 `outline`, `border`, `box-shadow`가 살아있거나 상위 컨테이너의 일괄 `:focus-visible` 규칙에 걸려 외곽 둥근 테두리 안에 사각 파란색 테두리가 겹쳐 뜨는 이중 박스 결함(네모 안의 네모)을 원천 차단한다. 내부 입력 필드는 `outline: none; border: none; box-shadow: none;`으로 평탄화(Unbox)하고, 외곽은 과도한 2px 원색 아웃라인 대신 부드러운 소프트 글로우(`box-shadow: 0 0 0 3px var(--primary-soft)`)로 절제한다.
- **입력기 모드 전환 시 UI 레이아웃 급변 및 외곽 탈출 방지 (Consistent Surface & In-Region Toolbar)**: 동일한 작성 영역에서 토글 버튼으로 작성 모드를 변경할 때 입력창 형태(둥근 알약형 ↔ 각진 박스형)나 높이, 라벨 유무가 갑자기 뒤바뀌며 덜컹거리는 UI 점프를 금지한다. 수신 대상이나 성격이 상이한 작업(글로벌 AI 질의 vs 특정 담당자 문의 스레드)은 모드 스위치로 강제 통합하지 않고, 각 문의 스레드에 바인딩된 독립 입력창으로 분리하여 다중 문의 대상의 모호성을 차단한다. 또한 '문의 내역' 등 보조 액션 버튼을 `position: absolute; bottom: calc(100% + 8px)`로 부모 컨테이너 바깥으로 띄워 날리지 않고 툴바 영역 내부의 인라인 흐름으로 정돈하며, 특정 역할 카드의 1면에만 굵은 테두리를 두르는 비대칭 보더를 지양하고 4면 균일 1px 보더를 사용한다.
- **검색창·액션 버튼 인라인 일체화 및 수직 이탈 방지 (Inline Search-Action Integrity & Zero Vertical Drop)**:
  - 툴바 및 필터 영역의 검색창(`<input type="search">`)과 `[검색]` 버튼은 분리된 박스나 `display: grid`로 인해 버튼이 아래 줄로 뚝 떨어져 분리되는 레이아웃 결함을 엄격히 금지한다.
  - 검색 입력과 버튼은 반드시 동일한 수평 flex 컨테이너(`display: flex; align-items: center; gap: 8px;`)로 결합하고, 버튼에는 `flex-shrink: 0; white-space: nowrap;`을 부여하여 좁은 화면에서도 한 줄 인라인 흐름과 일치된 높이를 보장한다.
  - 개별 사용자/계정/역할 등의 반복 목록은 카드 박스를 걷어내고 컴팩트한 단일 데이터 테이블로 전환하며, 긴 텍스트(소속 부서, 조직명)는 뭉뚱그리지 않고 독립 컬럼으로 명확히 분리한다.
- 제목 계층과 읽기 순서를 보존한다. 목록은 `ul`/`ol`, 라벨/값은 `dl`, 행·열 비교는 `table`을 의미에 맞게 사용한다. 선택 그룹의 `fieldset`/`legend` 등 접근성 구조를 제거하지 않는다.
- 색상만으로 상태를 전달하지 않는다. 보조정보도 읽을 수 있는 크기와 대비를 유지한다. 배경 명도 차이는 장식적 보조 수단이지 제목·상태 라벨의 대체가 아니다.
- 범용 selector로 모든 border/background/shadow를 지우거나 카드 개수·중첩 깊이만으로 자동 교정하지 않는다. 카드 수 감소율을 품질 점수로 제시하지 않는다.

## 5. 결과 검증과 인계

수정했다면 같은 내용·상태·뷰포트의 전후 화면을 비교하고 영향받는 기존 테스트/빌드를 실행한다. 실제 화면 확인 도구가 없으면 시각 검증 미실행을 명시한다.

- 첫 과업과 핵심 정보가 장식보다 먼저 보이는가?
- 관련 정보가 한 그룹으로 읽히고, 다른 그룹과 구별되는가?
- 클릭/선택 가능한 것과 정적 정보가 구별되고 키보드 포커스가 보이는가?
- 장식적 테두리를 덜어도 구조가 유지되는가? 모든 테두리를 없애는 실험은 하지 않는다.
- 요청한 뷰포트와 좁은 화면에서 긴 값·줄바꿈·빈 값·로딩·오류·선택 상태가 유지되는가? 확대 시 잘림과 불필요한 가로 스크롤을 확인한다.
- 복합 뷰어(Canvas/PDF/차트)가 다중 박스 패딩에 갇혀 불필요하게 과도 축소되거나, 조상 컨테이너 폭을 밀어내어 가로 스크롤을 유발하지 않는가?
- 축소/스퀸트 확인에서 박스보다 의도한 위계가 보이는가? 이 확인은 실제 읽기·접근성 검증을 대체하지 않는다.
- 남긴 카드마다 독립성·선택·중요 행동 등 이유를 설명할 수 있는가?
- 관리 화면이면 상단바·제목·탭·필터·표의 시작선이 일치하고, 제목이 탭 전환에도 메뉴 이름으로 유지되는가?
- 같은 설명 문장이나 같은 정보 묶음이 한 화면에 두 번 이상 나오지 않는가?
- 데이터 0건·일반·최대(가장 많은 계정/프로젝트) 세 상태를 모두 확인했는가? 혼재·반복·잘림은 최대 상태에서만 드러나는 경우가 많다.

인계는 `대상 → 제거/유지 이유 → 대체 방식 → 검증 결과`로 짧게 작성한다. 실제 확인한 것과 추정/미실행을 구분한다. 시각적 단순화만으로 사용성이 개선됐다고 입증한 것처럼 말하지 않는다.
